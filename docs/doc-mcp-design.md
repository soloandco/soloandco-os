# 사업 문서 MCP 설계

- 작성일: 2026-09-05
- 상태: 승인됨
- 위치: 이 저장소의 `packages/doc-mcp` (워크스페이스 패키지)
- 첫 사용처: 비공개 워크스페이스 하나 (경로는 `config.json`이 갖는다)

## 무엇을 푸는가

사업 문서가 바로 안 나오는 이유는 렌더링이 아니라 아래 셋이다.

- 값이 흩어져 있어 문서마다 사람이 찾아야 한다 (가격·연락처·고객이 서로 다른 문서에 있다)
- 돈 서류의 본문 서식이 없다 (체크리스트와 빈 표만 있다)
- 저장 위치와 파일명을 매번 사람이 정한다

MCP는 값과 저장을 맡고, 문장과 디자인은 호출하는 쪽(AI + 문체 스킬)이 맡는다.

## 이번 판 범위

**견적서 1종만 만든다.**

- 청구서·정산서는 대상이 아직 없다. 실제 입금 기록이 0건이고 요율이 서면 미확정이다
- 셋은 같은 부품을 쓴다. 견적서로 부품을 만들면 나머지는 서식 파일 추가로 끝난다
- 계약·사업·운영 서류는 다음 판이다

## 왜 이 저장소인가

이 저장소는 공개판이고 자체 규칙이 "실제 멤버·고객·계약·정산·금융·인증 데이터를 넣지 말 것"이다. 코드와 사용자 값을 섞으면 그 규칙에 바로 걸리므로, 분리를 사람이 기억하지 않아도 된다.

생성기와 섞이지 않도록 별도 패키지로 넣는다. 루트 `create-soloandco-os`의 `files` 목록과 의존성은 건드리지 않는다. 폴더만 만들려는 사용자에게 MCP 라이브러리가 딸려가면 안 된다.

## 그릇과 값의 분리

| 무엇 | 어디 | 공개 |
|---|---|---|
| 서버 코드, 서식 틀, 테스트 | `packages/doc-mcp/` | 공개 |
| 가격·연락처·색·저장 경로 | 사용자의 비공개 워크스페이스 | 비공개 |
| 둘을 잇는 설정 | `config.json` (gitignore) | 비공개. `config.example.json`만 공개 |

코드와 서식에 특정 워크스페이스의 값(금액·이메일·색 HEX·상호)을 넣지 않는다.

- **사실 값이 비어 있으면 멈추고 묻는다.** 가격·명의·연락처가 그렇다. 지어내면 대외 문서가 틀린다
- **스타일 값이 비어 있으면 무채색으로 낸다.** 색·서체가 그렇다. 문서는 나와야 한다

## 기술 선택

이 저장소의 기존 방식에 맞춘다. 새 도구 체계를 들이지 않는다.

- ESM JavaScript(`.mjs`). TypeScript를 도입하지 않는다
- 테스트는 `node:test` + `node:assert/strict`
- 설정은 `config.json`. YAML 파서를 새로 넣지 않는다
- 추가 의존성은 `@modelcontextprotocol/sdk` 하나뿐이다
- stdio 전송. 원격 서버와 인증은 만들지 않는다

## 도구 3개

| 이름 | 입력 | 하는 일 |
|---|---|---|
| `get_pricing` | 없음 | 정책 수치(모듈 시작가·요율)를 등록부에서 읽어 값·정본 경로·확인일과 함께 돌려준다 |
| `get_counterparty` | `slug` | 상대의 식별자·이름·단계·저장 폴더를 돌려준다 |
| `create_quote` | `counterparty`, `items[]`, `valid_days` | A4 HTML 견적서를 만들어 정해진 위치에 저장하고 경로를 돌려준다 |

문구 작성은 도구가 하지 않는다.

## 값의 출처

`config.json`이 아래를 가리킨다. 경로 이름은 워크스페이스마다 다를 수 있으므로 코드에 박지 않는다.

| 값 | 출처 형태 |
|---|---|
| 모듈 시작가, 수수료율 | 수치 등록부 마크다운의 표 (`수치 / 키 / 값 / 정본 / 확인일`) |
| 연락처·발행 명의 | 연락처 정본 마크다운의 표 (`항목 / 값`) |
| 상대 정보 | 파이프라인 마크다운의 표와 상대별 폴더. 표에 폴더 이름 열을 두면 그 값을 폴더로 쓰고, 열이 없으면 표시 이름을 폴더 이름으로 쓴다 |
| 색·서체 | `config.json`의 `brand` |
| 저장 위치 규칙 | `config.json`의 `output` |

등록부를 쓰는 이유는 그 표가 이미 검사 스크립트로 정본 문서와 대조되고, 어긋나면 커밋이 막히기 때문이다. 산문을 파싱하지 않아도 되고 값이 갈릴 수 없다.

## 견적서 사양

- 발행 명의가 개인이면 사업자등록번호란과 부가세 줄을 넣지 않고 단일가로 표시한다. `config.json`의 `issuer.business_number` 유무로 갈린다
- 출력은 A4 HTML 한 장. PDF 변환은 하지 않는다
- 저장 위치와 파일명은 `config.json`이 정한다
- 견적번호는 붙이지 않는다

## 보안

로컬 파일만 다루는 도구이므로 넷으로 한정한다.

1. 네트워크 호출을 하지 않는다. 외부로 나가는 경로 자체가 없다
2. `config.json`의 워크스페이스 루트 밖 경로는 읽기·쓰기 모두 거부한다
3. 읽은 값을 로그나 에러 메시지에 싣지 않는다
4. 문서에 들어가는 모든 문자열을 HTML 이스케이프한다

권한 관리·암호화·감사 로그는 넣지 않는다. 혼자 쓰는 로컬 도구에 맞지 않는 무게다.

## 안 만드는 것

- 청구서·정산서 서식
- 견적번호 발번과 이력 관리
- PDF 변환
- 원격 서버·인증
- 정산 계산 (요율이 서면 확정된 뒤에 붙인다)

## 끝났다고 말하는 기준

- 실제 리드 한 건으로 견적서를 끝까지 뽑는다
- 금액이 수치 등록부의 값과 일치하는지 자동 테스트로 고정한다
- A4로 인쇄했을 때 본문 텍스트와 표 내용이 상하 24mm·좌우 22mm 안전 여백을 침범하지 않는지, 600dpi 기준 0.05mm 오차범위로(표의 가는 구분선은 제외하고) 실측한다
- 워크스페이스 밖 경로 요청이 거부되는지 테스트로 고정한다
- 저장소 안 어디에도 실제 금액·이메일·색 HEX가 없는지 확인한다

## 실사용 검증 (2026-09-05)

실제 워크스페이스를 가리키는 config.json으로 가격·연락처·리드 값을 읽어 견적서 한 장을 실제로 생성했다. 헤드리스 크롬으로 PDF를 뽑아 600dpi로 래스터화한 뒤 픽셀 경계로 네 변 여백을 실측했다. 상단 약 26.6mm, 하단은 내용이 짧아 163mm 이상으로 여유가 컸다. 좌우는 각각 약 21.97mm, 21.89mm로 22mm 기준에 각각 0.03mm, 0.11mm 못 미쳤다. 600dpi 픽셀 하나의 크기는 0.042mm이므로 좌측 잔차(0.03mm)는 이 측정의 해상도 안에 있고, 우측 잔차(0.11mm)는 그보다 크다. `@page` 여백은 좌우 대칭(22mm)이므로 이 비대칭이 렌더링 단계와 측정 단계 중 어디서 비롯됐는지는 이번 측정만으로 밝혀지지 않는다.
